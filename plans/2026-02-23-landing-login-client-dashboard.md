## Overview

### What This Plan Accomplishes

The deployed dashboard at `https://rtadik.github.io/bobe-content-dashboard` currently auto-redirects straight to content — anyone with the URL can see everything. This plan adds a landing page, a login form, and per-client session authentication so that each client logs in with their own credentials and sees only their own content dashboard. The admin login routes to the existing admin panel.

### Why This Matters

As more clients are onboarded, data isolation becomes essential. Clients should not see each other's content. The landing page also provides a professional entrypoint to the platform — it's the first thing a client sees, and its design will be finalized in a follow-up session.

## Design Decisions

### Key Decisions Made

1. **Credentials baked into login.html, not served as JSON**: The hashed credential map is injected directly into the HTML of `login.html` at build time. This avoids a publicly-fetchable `/clients-auth.json` endpoint. SHA-256 hashes are one-way, so even if the source is visible, passwords can't be reversed (with strong passwords).

2. **SHA-256 via Web Crypto API**: Browser-native `crypto.subtle.digest('SHA-256', ...)` — no external library needed, works on all modern browsers, async Promise-based.

3. **sessionStorage, not localStorage**: Session is cleared when the tab/browser closes. Clients must re-login on new sessions. Same pattern used by the existing admin panel PAT storage.

4. **Per-client subdirectory (`dist/dashboard/{client_id}/`)**: Keeps client content isolated in the filesystem. Relative image paths (`images/filename.png`) remain unchanged inside the subdirectory.

5. **Admin login → redirect to /admin/**: Admin credentials route to the existing PAT-based admin panel. No changes to admin panel logic. Admin enters their PAT there as before.

6. **Placeholder landing page design**: Minimal dark-theme page with brand name, one-liner tagline, and a "Log In" button. Marked visually as a placeholder. Full design to be completed in a future session.

7. **Credentials source: `credentials.json` (local) or `DASHBOARD_CREDENTIALS` env var (CI)**: For local builds, `credentials.json` is gitignored. For GitHub Actions, the JSON content is stored as a repository secret and passed as an environment variable.

8. **No Python-side SHA-256 pre-hashing**: Passwords are hashed by `build_static.py` using Python's `hashlib.sha256` before injecting into the HTML. This means plaintext passwords only exist in `credentials.json` (gitignored) and the GitHub Secret. The deployed HTML contains only hashes.

### Alternatives Considered

- **URL token routing** (e.g., `/dashboard/secret-abc123/`): simpler, no login form, but user explicitly requested a login UI.
- **Serverless function auth** (e.g., Cloudflare Worker, Netlify function): more secure, but requires changing hosting from GitHub Pages. Overkill for content visibility.
- **GitHub OAuth**: robust but requires a backend callback URL. Not compatible with static GitHub Pages.
- **Separate `clients-auth.json` file**: cleaner separation, but exposes the hash map to anyone who knows the URL. Inline injection is slightly better.

### Step 4: Update build_static.py — add credential loader

Add a `load_credentials()` function at the top of `build_static.py` that:
1. Tries to read `DASHBOARD_CREDENTIALS` environment variable (for CI)
2. Falls back to reading `credentials.json` from the project root (for local dev)
3. If neither exists, returns an empty list (build proceeds, auth disabled with a warning)
4. Hashes each password using `hashlib.sha256(password.encode()).hexdigest()`
5. Returns a list of credential objects with `username`, `password_hash`, `client_id`, `role`, `display_name`

**Actions:**

- Add import: `import hashlib` at top of `build_static.py`
- Add the `load_credentials()` function after the imports section:

```python
def load_credentials():
    """Load and hash credentials from credentials.json or DASHBOARD_CREDENTIALS env var.

    Returns list of dicts: {username, password_hash, client_id, role, display_name}
    """
    import hashlib
    raw = None

    # Try env var first (for GitHub Actions)
    env_creds = os.environ.get("DASHBOARD_CREDENTIALS")
    if env_creds:
        try:
            raw = json.loads(env_creds)
        except json.JSONDecodeError:
            print("  Warning: DASHBOARD_CREDENTIALS env var is not valid JSON, skipping")

    # Fall back to credentials.json
    if raw is None:
        creds_path = Path(__file__).parent.parent / "credentials.json"
        if creds_path.exists():
            with open(creds_path) as f:
                raw = json.load(f)

    if raw is None:
        print("  Warning: No credentials found. Login will show 'Auth not configured'.")
        return []

    result = []
    for entry in raw.get("clients", []):
        password = entry.get("password", "")
        result.append({
            "username": entry.get("username", ""),
            "password_hash": hashlib.sha256(password.encode()).hexdigest(),
            "client_id": entry.get("client_id", ""),
            "role": entry.get("role", "client"),
            "display_name": entry.get("display_name", entry.get("client_id", "")),
        })
    return result
```

// Credentials map injected at build time (SHA-256 hashed passwords only)
const CREDENTIALS = {{ credentials_json }};

async function sha256(message) {
  const msgBuffer = new TextEncoder().encode(message);
  const hashBuffer = await crypto.subtle.digest('SHA-256', msgBuffer);
  const hashArray = Array.from(new Uint8Array(hashBuffer));
  return hashArray.map(b => b.toString(16).padStart(2, '0')).join('');
}

async function handleLogin() {
  const username = document.getElementById('username').value.trim();
  const password = document.getElementById('password').value;
  const btn = document.getElementById('login-btn');
  const errEl = document.getElementById('error-msg');

  if (!username || !password) {
    errEl.textContent = 'Please enter both username and password.';
    errEl.classList.add('show');
    return;
  }

  btn.disabled = true;
  btn.textContent = 'Checking...';
  errEl.classList.remove('show');

  try {
    const hash = await sha256(password);
    const match = CREDENTIALS.find(c => c.username === username && c.password_hash === hash);

    if (!match) {
      errEl.textContent = 'Incorrect username or password.';
      errEl.classList.add('show');
      btn.disabled = false;
      btn.textContent = 'Log In';
      return;

    // Store session
    sessionStorage.setItem('dash_auth', JSON.stringify({
      clientId: match.client_id,
      username: match.username,
      role: match.role,
      display_name: match.display_name
    }));

    // Redirect based on role
    if (match.role === 'admin') {
      window.location.href = 'admin/';
    } else {
      window.location.href = 'dashboard/' + match.client_id + '/';
    }
  } catch (err) {
    errEl.textContent = 'Login error. Please try again.';
    errEl.classList.add('show');
    btn.disabled = false;
    btn.textContent = 'Log In';
  }
}

  if (e.key === 'Enter') handleLogin();
});

## Notes

- **Landing page redesign**: The placeholder design uses minimal dark-theme styling matching the existing system. A full branded landing page design will be a separate session/task with deliberate visual choices.
- **Multi-client expand**: When a second client is onboarded, their dashboard will be built at `dist/dashboard/{new_client_id}/`. The login system already supports multiple entries in `credentials.json`. No structural changes needed.
- **Password rotation**: To change a password, update `credentials.json` (or the `DASHBOARD_CREDENTIALS` GitHub Secret) and redeploy. Sessions are in `sessionStorage` and expire on browser close.
- **Security posture**: This is soft client authentication suitable for content visibility. It is not appropriate for protecting payment data or PII. The threat model is: preventing casual URL-sharing between clients, not defending against targeted attacks.
